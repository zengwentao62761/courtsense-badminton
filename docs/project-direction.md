# 两条工程主线与产品方向

更新：2026-11-08。本页整理开发目标与仓库职责。当前实现仍为P0.2.0；手机推理、章级教学和多路场馆部署均未实现。

## 仓库职责

| 主线 | 用途 | 当前关系 |
| --- | --- | --- |
| 原Codeup `ai-coach` | 保留RDK姿态部署、历史工作台、微调量化实验和版本恢复依据 | 作为历史实测与工程经验来源；不因新项目改动而自动升级原服务 |
| GitHub `courtsense-badminton` | 当前主要开发与地瓜机器人黑客松公开项目 | 完善可运行分析、具身扩展、验证记录和报名材料 |

旧“姿态识别”工程是保留历史的第三个本地仓库，不是GitHub的另一份同目录副本。旧姿态提交在原总工程历史中保留；CourtSense当前明确迁入三个姿态基础文件，来源见[迁移记录](migration.md)与[第三方说明](../THIRD_PARTY_NOTICES.md)。

Codeup与GitHub不是同一仓库的双远端，也不按目录全量镜像。复用按模块记录源提交、许可、契约和验证；硬件驱动、相机所有权、模型与运行服务分别处理，避免两个进程争用单MIPI。新任务默认落在CourtSense，旧部署的历史性能不能当作新版本性能。

## 当前参赛重点与长期目标

当前重点是RDK具身训练原型：采集来源可追溯，场线与地面位置可验证，人—球—拍事件有共同时间语义，再由真实到位、回中与设备反馈推进训练。移动底盘、云台、球拍IMU是下一阶段三个关键扩展，详见[设备设计](embodied-expansion.md)与[任务清单](extension-tasks.md)。

长期目标是让教练和学员以更低的单场成本使用完整的羽毛球AI Coach。需求来自多片场地部署的成本问题，希望探索4—6片场地的使用情形；这不是当前已支持的并发路数或已签约的场馆数量。

手机App、小程序或网页是潜在产品入口，也可进一步研究手机本地视觉。平台尚未定型。建议近期先接设备配置、训练记录和报告浏览，再比较手机自主采集/推理与场馆集中分析两条路线；这是一项实施建议，不取消实时手机视觉的长期目标。响应式网页现已检查窄屏布局，不等于已完成App、小程序、手机摄像头或手机端模型。

## 远景与近景使用不同观察条件

| 模式 | 面向的训练问题 | 需要验证 |
| --- | --- | --- |
| 远景全场 | 场线、球员位置、移动分布、回位、起跳与击球事件 | 镜头覆盖、足部可见性、地面参考、球体像素尺寸和真实时间 |
| 近景专项 | 拍柄与前臂的可见关系、手部和挥拍动作阶段 | 球拍/手部专门观测、机位适用范围、持拍侧与教师标注 |

同一17点骨架不提供拍面方向、球体深度或肌肉发力。远景不能假设仍看得清手部细节；近景也不能天然提供全场跑位。可先输出有依据的动作阶段与运动学线索，真实关节力、肌肉力或精确力矩需要额外方法和参考测量。

羽毛球高度、三维轨迹和真实球速仍是独立研究任务。球场平面标定不恢复空中球体深度，转动云台跨时扫描也不是动态球体的同步多视图测量。

## 体育教学视频与章节知识库

需求方表示已与体育老师合作，对方有训练教学视频；尚未完成本项目的数据接入和评价标准验收。下一步先选一个得到使用许可的教学章节，建立结构化条目：

- 章节与动作名称、适用对象、持拍侧、机位和版本。
- 示范片段起止时间、动作阶段、教师确认的观察要点。
- 能测量的指标、不可观察条件、错误示例及解释依据。
- 学员片段与示范片段的对应证据，以及教师复核状态。

先做“选章节—看示范—看学员证据—给下一项练习”的可复盘流程。动作序列的阶段对齐和速度归一化需要另行实验；不能将逐帧几何差异直接当成专业评分。知识检索或大模型解释必须关联具体章节和证据，不由自由生成文本直接决定动作等级。

教学视频、人物授权和对外展示范围分别确认。公开仓库仅放结构与去标识示例，不自动发布教师原视频、学员素材或对话全文。

## 降本路线的比较方法

| 候选方式 | 要回答的问题 | 当前状态 |
| --- | --- | --- |
| RDK具身训练站 | 停靠、观察、事件同步与实体反馈能否完整运行 | 现有姿态基础；新整合版与三设备待实测 |
| 手机本地视觉 | 不同机型持续运行时的时延、发热、画质和模型支持 | 产品需求，未做手机实机测试 |
| 手机作为入口 | 训练配置、记录与报告是否方便教练使用 | 现有响应式工作台；原生/小程序与设备控制待开发 |
| 场馆集中分析 | 一台主机能承受多少路、总延迟/带宽/布线如何 | 候选部署架构，未选型与压测 |

单场成本按相机、支架、算力、供电、网络、存储、安装维护与并发实测分别核算。复用现有手机或主机也需计入占用和持续运行成本，不把“已有设备”直接计为零。未经比较实验不承诺几路视频、固定FPS或降本比例。

## 跨平台复用

优先复用坐标与时间定义、事件标签、分析接口、教师章节结构和验证数据。各平台的采集和推理分别适配，保留原始模型来源、关键点拓扑、裁剪/旋转、置信语义及版本。

RDK官方流程从模型输入经工具链生成处理器运行产物；不能默认将已编译的BPU `.bin` 反向导成可移植ONNX。手机迁移应寻找原始模型/可导出权重，或重新选取合适的移动端模型，再单独验证。参考[官方PTQ流程](https://developer.d-robotics.cc/rdk_x_doc/Advanced_development/toolchain_development/intermediate/ptq_process)。

关键点数量也须显式转换：MoveNet定义17点，MediaPipe Pose Landmarker定义33点，名称、索引及坐标含义不同；人体模型输出的三维坐标不自动成为球场全局坐标。参见[MoveNet官方说明](https://www.tensorflow.org/hub/tutorials/movenet)与[Pose Landmarker官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker?hl=en)。本项目尚未集成这两个移动端候选。
